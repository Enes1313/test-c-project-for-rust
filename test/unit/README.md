# Test with Rust 🦀

*Read this in other languages: [English](README.md), [Türkçe](README.tr.md)*

This template provides a robust, highly automated, and memory-safe testing framework for C projects using Rust. It acts as a modern alternative to tools like Ceedling (Unity/CMock), bringing Rust's powerful ecosystem, strict type-checking, and parallel execution to legacy C codebases.

## ✨ Features

- **Automated Mock Generation:** Automatically generates mock modules for all C headers using `bindgen` and `mockall`.
- **Zero Boilerplate:** Defines mocks via simple `.toml` configuration files using arrays.
- **Hierarchical Collision Protection:** Mirrors the C project's folder structure in the Rust environment, preventing naming collisions.
- **Test Isolation:** Uses GNU Linker flags (`-ffunction-sections`, `-fdata-sections`) to ensure perfect test isolation and symbol resolution.
- **Coverage Ready:** Supports seamless integration with `gcovr` by passing `--coverage` or `-fprofile-arcs` to both your compiler and linker arguments.

## 🚀 Getting Started

### 1. Prerequisites
You need the standard Rust toolchain and Clang (for `bindgen`):
```bash
# Ubuntu/Debian
sudo apt install build-essential clang llvm
```

### 2. Configuration (`Cargo.toml` & `.cargo/config.toml`)
All framework settings are defined in `Cargo.toml` under `[package.metadata.foreigntest]`:
* `project_path`: Path to the C project root.
* `compile_args`: Arguments sent to the C compiler and `bindgen` (e.g., `-std=c99`, `-m32`, `-DDEBUG=1`, `-I../custom_lib`).
* `linker_args`: Arguments sent to the GNU Linker (e.g., `-lm`).
* `compile_commands_path`: Path to your `compile_commands.json` (e.g., generated by CMake). `build.rs` will automatically parse this JSON to extract all `-I`, `-isystem`, and `-D` flags.

**Important:** If `compile_commands.json` is successfully parsed, the slow brute-force recursive inclusion of `**/*.h` directories is automatically skipped!

> **💡 Note on Cargo.lock:** `Cargo.lock` handles Rust package versions. You can safely delete it or add it to `.gitignore`; running `cargo test` will regenerate it.

## 🏗 Architecture: Unit vs Integration Tests

Since this template is designed to test an external C library, **all tests are technically Rust integration tests**. However, we logically divide them into Unit and Integration testing:

* **Unit Tests:** A unit test isolates a single C module by compiling its source file and mocking all its dependencies (other C modules it calls).
* **Integration Tests:** An integration test compiles multiple C modules together without mocking their internal interactions, allowing you to test how they work as a subsystem.

You can organize your tests within the `tests/` directory however you like:
* **Per Module:** One test file (e.g., `test_app_example.rs`) containing all test functions for that module.
* **Per Scenario/Function:** Multiple test files in a folder (e.g., `tests/app_example/test_init.rs`, `tests/app_example/test_run.rs`). Cargo runs them all automatically.

## 🛠 How to Write a Unit Test

### 1. Define the Spec (`spec/`)
Create a `.toml` file mirroring the path of the C file you want to test. (e.g., `spec/source/app/app_example.toml`)

Define the headers, sources, and mocks using **Arrays** and strict relative paths:
```toml
headers = ["source/app/app_example.h"]
sources = ["source/app/app_example.c"]
mocks   = ["lib/lib_example", "source/util/util_example"]
```
*(If `headers` or `sources` are omitted, `build.rs` will attempt to infer them from the TOML file's name and location).*

### 2. Write the Test
In your test file (`tests/test_app_example.rs`), import the automatically generated `bindings` and `mocks` using `#[path]`. They strictly follow your C project's folder hierarchy!

```rust
#![feature(c_variadic)] // Only if testing variadic C functions

// 1. Import the C types (Bindings)
#[allow(non_upper_case_globals, non_camel_case_types, non_snake_case, unused)]
#[path = "../bindings/source/app/app_example.rs"]
pub mod app_example;
use app_example::*;

// 2. Import the Mocks
#[allow(non_snake_case, unused)]
#[path = "../mocks/source/app/app_example_mocks.rs"]
pub mod mocks;
use mocks::*;

#[cfg(test)]
mod app_tests {
    use super::*;

    #[test]
    fn test_initialization() {
        // 3. Setup mock expectations
        let ctx = mock_lib_example::lib_example_init_context();
        ctx.expect().once().returning(|| true);
        
        // 4. Call the real C function
        unsafe {
            app_example_init();
        }
    }
}
```

> **Warning:** C global `static` variables persist across multiple `#[test]` functions if they run in the same executable. To prevent state contamination, this framework enforces running tests sequentially by setting `RUST_TEST_THREADS = "1"` in `.cargo/config.toml`. You may also need to reset the C state manually at the start of each test.

## 🤝 How to Write an Integration Test

Integration tests verify that multiple C modules work together correctly without mocking their interactions. 

### 1. Define the Spec
To create an integration test, define a `.toml` file (e.g., `spec/integration/app_subsystem.toml`) and include **multiple** source files in the `sources` array. Omit them from the `mocks` array so their real implementations are compiled and linked together.

```toml
headers = ["source/app/app_example.h", "source/util/util_example.h"]
sources = ["source/app/app_example.c", "source/util/util_example.c"]
# Notice we do NOT mock util_example here!
mocks   = ["lib/lib_example"] 
```

### 2. Write the Test
In your Rust test (`tests/test_app_subsystem.rs`), you can now call functions from `app_example.c` and assert that they correctly interact with the real `util_example.c` logic, while only mocking the external `lib_example` boundary.

```rust
// 1. Import the C types for both modules
#[allow(non_upper_case_globals, non_camel_case_types, non_snake_case, unused)]
#[path = "../bindings/integration/app_subsystem.rs"]
pub mod app_subsystem;
use app_subsystem::*;

// 2. Import the Mocks (only lib_example is mocked)
#[allow(non_snake_case, unused)]
#[path = "../mocks/integration/app_subsystem_mocks.rs"]
pub mod mocks;
use mocks::*;

#[cfg(test)]
mod subsystem_tests {
    use super::*;

    #[test]
    fn test_subsystem_integration() {
        // We only mock the lower-level library
        let ctx = mock_lib_example::lib_example_init_context();
        ctx.expect().once().returning(|| true);
        
        unsafe {
            // Calling this will internally call real util_example functions!
            app_example_init(); 
        }
    }
}
```

## 🎭 Advanced Testing Features

### Overriding Hardware Macros (`support/` directory)
In embedded projects, you often have hardware macros like `*(int *)60 = 124;` which will cause a Segmentation Fault on PC. 
To bypass this, copy the problematic header to the `support/` folder (e.g., `support/header_mxu.h`) and edit the macro (e.g., `int x; #define REG_A (&x)`).
**`build.rs` always prioritizes the `support/` directory for includes (`-I`).** Both `cc` and `bindgen` will read your overridden header instead of the original C file!

### Testing the C `main` Function
To test the `main()` function of your C program without conflicting with Rust's internal test runner `main`, add a define to your `compile_args` in `Cargo.toml` or `compile_commands.json`:
* `-Dmain=app_main`
This renames the C entry point to `app_main`. You can then call `unsafe { app_main(); }` from your Rust tests!

## 🔧 32-Bit Toolchains and Sysroots

If your embedded C code is strictly 32-bit, you must pass `-m32` to the `compile_args` in `Cargo.toml`. 

**CRITICAL:** Passing `-m32` compiles the C library in 32-bit, but Rust defaults to 64-bit on modern OSs. The linker will crash with an *incompatible architecture* error.

To solve this, `.cargo/config.toml` defaults the `build.target` to `i686-unknown-linux-gnu` (32-bit):
```toml
[build]
target = "i686-unknown-linux-gnu"
rustflags = ["-C", "instrument-coverage"]

[env]
RUST_TEST_THREADS = "1"
CARGO_PROFILE_TEST_INCREMENTAL = "0"
LLVM_PROFILE_FILE = "target/profraw/cargo-test-%p-%m.profraw"
```

1. **If this 32-bit target is not installed on your system, you must add it first:**
   ```bash
   rustup target add i686-unknown-linux-gnu
   ```
2. **Install 32-bit System Libraries (Ubuntu):**
   ```bash
   sudo apt install gcc-multilib g++-multilib
   ```
3. **Run Tests:**
   You no longer need to specify `--target`, just running `cargo test` is enough. If you want to test a 64-bit C project, you can simply delete the `target` configuration in `.cargo/config.toml` or change it to your desired 64-bit target.

## 🧪 Code Coverage

To generate coverage reports, ensure `-fprofile-arcs` and `-ftest-coverage` (or `--coverage`) are present in `compile_args`, and `--coverage` is added to `linker_args` in your `Cargo.toml`.

Run tests and generate an HTML report using `gcovr` (which perfectly handles GCC coverage):
```bash
# 1. Install gcovr if you haven't already
pip install --user gcovr --break-system-packages

# 2. Clean and run tests to generate coverage data
cargo clean
cargo test

# 3. Generate HTML report
mkdir -p coverage
~/.local/bin/gcovr -r ../test-c-project-for-rust --object-directory target/i686-unknown-linux-gnu/debug/build/ --html-details -o coverage/index.html
```
